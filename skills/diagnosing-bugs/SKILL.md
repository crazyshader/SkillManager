# 排查 Bug

按阶段推进。只有在有明确理由时才跳过某个阶段。

阅读代码前，如果存在 `GLOSSARY.md`，先读它；同时检查相关模块的 ADR（架构决策记录）。

## 脱敏

展示命令、输出或抓包内容前，把密钥、token、密码替换为 `<REDACTED>`。检查命令从环境变量读取凭据，凭据不写进代码或展示内容。只引用包含错误信息的行。

脱敏后的输出不足以定位问题时，告诉用户缺什么，并请用户补充。

## 阶段 1：建立检查命令

目标是一条**能稳定复现问题的命令**，之后的缩小范围、假设验证和加日志都依赖它。没有这条命令，只能靠读代码猜原因，结果不可靠。

按以下顺序选择构造方式，优先用靠前的方式：

1. 在能触达该 bug 的层级写失败测试（单元、集成或端到端）。
2. 对运行中的开发服务器执行 curl 或 HTTP 脚本。
3. 用固定输入调用 CLI，把 stdout 与已知正确的结果比对。
4. 用无头浏览器（Playwright、Puppeteer）操作界面，检查页面、控制台或网络请求。
5. 保存真实的请求、载荷或事件日志，离线重放到代码路径中。
6. 搭一个最小的临时环境，只保留出问题的代码，用一次函数调用触发。
7. 对"偶尔输出错误"的情况，用随机或模糊输入运行上千次，找出失败样本。
8. 若 bug 出现在两个已知版本之间，写一个"切换到某版本、检查、重复"的脚本，交给 `git bisect run`。
9. 对同一输入分别运行旧版和新版（或两套配置），比较输出差异。
10. 只有在必须由人操作时，才用人工参与的脚本驱动，并把人的操作结果回传给 agent。

让检查命令更好用：
- 更快：缓存初始化，跳过无关步骤，缩小测试范围。
- 更准：断言用户看到的具体症状，而不是"没有崩溃"。
- 更稳定：固定时间，固定随机种子，隔离文件系统，冻结网络。

**非确定性 bug**：目标是提高复现率，而不是得到每次都成功的复现。把触发动作重复 100 次，并行执行，提高并发数（例如从 1 个并发增加到 16 个），减少两个操作之间的时间差，使竞争条件更容易出现。复现率 50% 的 bug 可以调试；复现率 1% 的，需要继续提高复现率。

**无法建立检查命令时**：说明已尝试的方法，并请用户提供以下任一项：(a) 能复现问题的环境，(b) 脱敏后的抓包或日志（HAR、日志、core dump、带时间戳的录屏），(c) 授权添加临时的线上诊断。没有检查命令时，不进入假设阶段。

**阶段 1 完成标准**：已有一条命令，并且至少运行过一次（展示命令和脱敏后的输出），同时满足以下四项：
- [ ] **能复现失败**：命令走的是真实的 bug 代码路径，断言的是用户描述的具体症状。
- [ ] **结果稳定**：每次运行的结论相同（非确定性 bug 需要达到稳定的高复现率）。
- [ ] **速度快**：秒级完成，不需要几分钟。
- [ ] **不需要人在场操作**：只在必要时由人通过人工脚本参与。

如果在有检查命令之前就开始读代码推理原因，立即停下，先建立检查命令。

## 阶段 2：复现并缩小范围

运行检查命令，确认它按预期失败。确认以下三项：
- [ ] 失败现象与用户描述的一致，不是附近的另一个错误。否则修复的会是错误的问题。
- [ ] 多次运行都能复现（非确定性 bug 达到足够高的复现率）。
- [ ] 记下具体症状（错误信息、错误输出、耗时），修复后用它验证。

**缩小范围**：每次删掉一项输入、调用方、配置、数据或步骤，然后重新运行检查命令。只保留失败所必需的部分。

完成标准：剩下的每一项都是必需的，删掉任何一项，检查命令就会通过。

没有完成复现和缩小范围，不进入下一阶段。

## 阶段 3：提出假设

在验证任何假设之前，先列出 **3 到 5 个按可能性排序的假设**。只列一个假设，容易被第一个想到的答案带偏。

每个假设都必须**可证伪**，写清预测，格式如下：

> "如果原因是 X，那么改动 Y 会让 bug 消失"，或"改动 Z 会让 bug 更严重"。

写不出预测的假设只是猜测。删掉它，或改写得更具体。

开始验证前，把排好序的列表给用户看。用户可能掌握相关背景，能调整排序（例如"我们刚部署了与 #3 相关的改动"），也可能已经排除了某些假设。用户不在线时，按自己的排序继续。

## 阶段 4：加探针

每个探针都对应阶段 3 中的某个预测。**每次只改动一个变量。**

完成标准：每个探针都能说出它检验的是哪个预测，并且每次只改动了一个变量。

探针的选择顺序：
1. 环境支持时，用调试器或 REPL 检查变量。一个断点比多条日志更直接。
2. 在能区分假设的位置加针对性日志。
3. 不要把所有变量都打印出来再用 grep 查找。

**给每条调试日志加唯一前缀**，例如 `[DEBUG-a4f2]`。结束时按前缀搜索，就能一次删除全部调试日志。没有前缀的日志容易遗留在代码里。

## 阶段 5：修复并加回归测试

先写回归测试，让它在修复前失败。修复后它通过。阶段 2 得到的最小复现如果本身就适合作为测试，直接使用它。

修复要能解释根因，而不只是让报错消失。

完成标准：修复前回归测试失败，修复后通过；阶段 1 的检查命令不再出现用户描述的症状；其他测试的结果与修复前一致。

## 阶段 6：清理

- 按调试前缀删除全部临时日志。
- 删除临时脚本和测试夹具，除非用户希望保留。
- 向用户报告：根因、验证方式、回归测试的位置、仍存在疑问的地方。
