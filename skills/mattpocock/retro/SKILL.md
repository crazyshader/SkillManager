用户要求做一次**复盘**。你要提出改进 coding agent 工作环境的建议，让后续运行减少返工或重复出错。

## 步骤

1. 每条建议写明两点：涉及的文件或场景，以及建议的具体改动。

2. 阅读用户指定会话的原始记录。需要时可以在本机搜索会话日志。用户没有指定会话时，复盘当前会话，并在报告开头写明"仅覆盖当前会话"。

3. 按以下类别寻找可改进之处：

- **导航**：agent 能否快速找到正确的文件？文件之间有没有隐藏的依赖？加一个指向相关文件的索引行能否减少查找时间？*适用场景*：会话花了很长时间才找到某个信息。
- **自动检查**：有没有自动检查能在 agent 出错时报告失败，例如 lint、类型检查、测试、文件系统检查？先读仓库自己的检查命令（`package.json` 或构建工具里的 `lint`、`check` 脚本，以及 CI 配置）。如果检查已经存在，但没有接入或已经失效，这本身就是发现，不要重新写一个。如果仓库没有任何自动检查（没有 pre-commit 钩子，CI 中也不运行 lint、类型检查或测试），这也是发现，应当补上。*适用场景*：agent 的错误本可以被自动检查提前发现，或仓库完全没有自动检查。
- **编码规范**：是否应该给审查 agent 增加一条编码规范？是否应该删除或修改现有编码规范？先判断违规的类型。**可以用固定规则判断的违规**（如禁用的 API、固定的 import 写法、文件位置）应该做成确定性检查，例如仓库 linter 的自定义规则、pre-commit 钩子或 CI 任务，选当前语言和现有检查下成本最低的方式。只有**需要人判断的内容**（如跨文件的一致性、"与周围风格保持一致"，以及任何自动检查都无法替代的内容）才写进 `CODING_STANDARDS.md`。*适用场景*：审查 agent 没有发现某个错误。
- **全局 AGENTS.md**：有没有指令应该改为编码规范或自动检查？*适用场景*：AGENTS.md 很长，无论是仓库内的还是用户全局的。
- **工具调用成本**：agent 有没有做过昂贵、可以精简的工具调用？有没有 token 消耗很高的自定义工具（CLI 或 MCP）？*适用场景*：agent 做过一次昂贵的工具调用。
- **无效指令**：找出不会改变 agent 行为的指令。*适用场景*：指令文件很长，难以维护。
- **信息获取**：agent 能否获得更多它需要的信息？例如转发开发服务器日志，或只读访问第三方服务。*适用场景*：agent 无法获取某条必需的信息。

4. 按对后续运行的影响排序（会导致 agent 再次出错的排在前），把改进建议呈现给用户。完成标准：每条建议都写明类别、依据的会话片段和建议的动作，并按步骤 4 定义的影响顺序排列。

## 参考

### 实现与审查的分工

工作分两个阶段：实现和审查。实现 agent 需要读取的内容最多：探索代码、写代码、调试失败。

审查 agent 只收到一份 diff，不需要探索代码，通常也不写代码或调试。

因此，**编码规范由审查 agent 执行，实现 agent 不承担这项工作**。

### 各类文件的职责

- `CLAUDE.md` 或 `AGENTS.md`：这些文件会被放进在该仓库工作的每个 agent 的上下文。应尽量少用，通常只放指向其他文件的索引行。
- `CODING_STANDARDS.md`：在审查阶段读取，实现阶段不读。文件超过 1000 行时，在开头添加指向各文档的索引行。
- 上述文件不存在时，跳过依赖它的检查，并在报告中注明"仓库无 CODING_STANDARDS.md"。不要凭空假设它的内容。
- 文档是参考资料，由其他文件指向。写新文档前先查看现有文档。
- Skill：用于文档（它的 description 会进入 agent 上下文），或用于用户触发的命令。按 `writing-for-agents` skill 的建议编写。
