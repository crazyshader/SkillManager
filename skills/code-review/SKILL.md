审查 `HEAD` 与用户指定的起点之间的 diff，从两个维度给出结论：

- **Standards**：代码是否符合仓库记录的编码规范。
- **Spec**：代码是否实现了原始 issue 或 spec 的要求。

两个维度分别由子代理并行执行。每个子代理使用全新上下文，互不影响。最后由发起审查的主代理汇总结果。

## 流程

### 1. 确定起点

用户给出的任何形式（commit SHA、分支名、tag、`main`、`HEAD~5`）都是起点。用户没有指定时，先询问。

记录 diff 命令：`git diff <起点>...HEAD`（三点语法，与共同祖先比较）。同时记录提交列表：`git log <起点>..HEAD --oneline`。

继续之前，确认起点能解析（`git rev-parse <起点>`），并且 diff 非空。起点无效或 diff 为空时，在这一步停止并告诉用户，不启动子代理。

### 2. 找到需求来源

按顺序查找：
1. 提交信息中的 issue 引用（`#123`、`Closes #45` 等）。能读取到 issue 内容时使用；读取不到时，把 issue 编号告诉用户，请用户提供内容。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 中与分支名或功能名匹配的 spec 文件。
4. 都找不到时，询问用户需求在哪里。用户说没有时，跳过 Spec 子代理，并在报告中注明"无 spec 可用"。

### 3. 找到规范来源

搜索仓库中所有记录编码规范的文件。存在 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md` 时，必须列入。

Standards 维度除了仓库规范，还附带下面的**代码结构检查清单**。使用清单时遵守两条规则：

- **仓库规范优先**。仓库明确允许的做法，即使清单条目匹配，也不报告。
- **代码结构检查清单只提供判断依据**。每条发现都写成"可能存在 X"，不作为硬性违规。工具已经检查的内容跳过。

清单条目（每条写明：现象 → 处理方式）：
- **名字不能说明用途**：函数、变量或类型的名字看不出它做什么或保存什么。→ 改名。如果想不出准确的名字，说明设计本身不清楚。
- **同样的逻辑重复出现**：同一段逻辑出现在改动的多个代码块或文件中。→ 提取公共部分，两处都调用它。
- **方法总在访问别的对象的数据**：某个方法读取其他对象的字段次数多于读取自己的字段。→ 把方法移到它主要使用的数据所在的对象上。
- **几个值总是成组出现**：几个字段或参数总是一起传递，说明它们应该是一个类型。→ 打包成一个类型再传递。
- **用原始类型代替领域概念**：用字符串或数字表示一个有业务含义的值（如金额、手机号）。→ 为该概念定义一个小类型。
- **同一判断在多处重复**：同一类型上的 switch 或 if 链在改动中多次出现。→ 改用多态，或用一张映射表供各处共用。
- **一次改动要改很多文件**：一个逻辑变更分散修改了 diff 中的许多文件。→ 把一起变化的代码移到同一个模块。
- **一个文件因多个原因被修改**：同一文件因为几件无关的事被改动。→ 拆分，让每个模块只因一个原因变化。
- **为 spec 之外的需求预留抽象**：为 spec 中不存在的需求添加了抽象、参数或钩子。→ 删除，等真正需要时再加。
- **长链调用**：调用方写出 `a.b().c().d()` 这样的长链，依赖了中间对象的结构。→ 把这段调用链封装成第一个对象上的一个方法。
- **只做转发的类或函数**：类或函数只是把调用原样转给另一个对象。→ 删除它，让调用方直接调用目标。
- **子类不用父类的大部分内容**：子类忽略或覆盖了它继承的大部分方法。→ 去掉继承，改用组合。

### 4. 并行启动两个子代理

两个子代理在同一条消息中一起启动，前台执行，然后汇总它们的报告。

**Standards 子代理的提示词**包含：
- 完整的 diff 命令和提交列表。
- 第 3 步找到的规范文件列表，以及**完整粘贴的代码结构检查清单**（子代理无法访问其他来源）。
- 任务要求："按文件或代码块报告：(a) 每处违反已记录规范的地方，引用规范（文件和具体规则）；(b) 每个命中清单条目的代码块，写出条目名称并引用对应代码。区分两类结论：违反仓库规范是硬性违规；符合清单条目的，属于判断项。仓库规范优先于清单。工具已检查的内容跳过。不超过 400 字。"

**Spec 子代理的提示词**包含：
- diff 命令和提交列表。
- spec 的路径或已获取的内容。
- 任务要求："报告：(a) spec 要求但缺失或只实现了一部分的需求；(b) diff 中做了但 spec 没要求的行为（范围蔓延）；(c) 看似已实现但实现有误的需求。每条发现都引用 spec 原文。不超过 400 字。"

没有 spec 时，跳过 Spec 子代理，并在最终报告中注明。

### 5. 汇总

用 `## Standards` 和 `## Spec` 两个标题展示两份报告。可以调整格式，但不改变结论。

两个维度的发现各自保持子代理给出的顺序，分开呈现。

最后用一行总结：每个维度各有多少条发现，并在每个维度内各自指出排在第一位的一条。两个维度独立判断，所以不做跨维度比较。

## 为什么分两个维度

一段改动可能通过其中一个维度，却未通过另一个：

- 完全符合规范，但实现了错误的需求 → **Standards 通过，Spec 失败**。
- 完全符合需求，却违反了仓库规范 → **Spec 通过，Standards 失败**。

分开报告，可以避免一个维度掩盖另一个维度。
